# product-factory

Самостоятельный набор скилов и агентов для [Claude Code](https://claude.com/claude-code) (и
совместимых агентов, например Cursor Agent): 16 скилов + 5 субагентов, которые проводят продукт
через весь цикл поставки — от идеи в одну строку до проверенной, протестированной и (опционально)
задеплоенной сдачи.

Репозиторий: [Dmkdok/product-factory](https://github.com/Dmkdok/product-factory).

## Что это даёт

Обычно у ИИ-агента есть только общий инструктаж и он импровизирует процесс поставки заново в каждом
проекте. `product-factory` фиксирует этот процесс один раз: единый пайплайн скилов ведёт продукт
через discovery → спецификацию → технический план → согласование с человеком → реализацию → тесты →
ревью → (опционально) деплой, плюс отдельные скилы на поведенческую дисциплину, экономию токенов,
безопасность и качество UI, которые можно подключать по ситуации.

## Установка

Вариант A — как плагин Claude Code, без изменений в самом проекте:

```bash
claude --plugin-dir /path/to/product-factory
```

`marketplace.json` для локального использования не нужен — `--plugin-dir` читает `plugin.json`
напрямую. Скилы вызываются с неймспейсом `/product-factory:orchestrate-product` и т.д., чтобы не
конфликтовать с одноимёнными скилами, если они уже есть в проекте.

Вариант B — вкопировать в проект:

1. Скопировать `skills/` и `agents/` этого репозитория в `.claude/` проекта — больше ничего
   подтягивать не нужно, шесть скилов-зависимостей ниже уже лежат внутри `skills/`.
2. Вставить содержимое `CLAUDE.product-factory.md` в `CLAUDE.md` проекта.
3. Скопировать `templates/` в проект как `templates/product-factory/` — `orchestrate-product`
   на Phase 0 сначала ищет шаблоны там.
4. Один раз прогнать скил `fewer-permission-prompts` (и `update-config` для хуков/прав), чтобы
   снизить трение от запросов на разрешение до того, как пайплайн начнёт генерировать вызовы
   инструментов в объёме.

## Как пользоваться

- Продукт с нуля → `/orchestrate-product`.
- В проекте уже есть `docs/SPEC.md`, нужно внести изменения (баг, правка от заказчика, рефакторинг,
  цель по производительности) → `/iterate-product`.

Оба скила сами проведут через остальные фазы пайплайна и сами вызовут нужные скилы и субагентов по
ходу работы — вручную запускать что-то ещё обычно не требуется.

## Пайплайн поставки (10 скилов)

| Скил | Что делает |
|---|---|
| `orchestrate-product` | Сквозной оркестратор поставки «с нуля»: ведёт через discovery, спецификацию, техплан, согласование с человеком, затем делегирует реализацию, тесты и ревью субагентам. |
| `iterate-product` | Тот же пайплайн, но для продукта, который уже работает: зелёный бейзлайн → приём правок → карта влияния и регрессий → поправки к SPEC/DECISIONS/TASKS → согласование → реализация → тесты → ревью. |
| `discover-requirements` | Въедливое интервью по требованиям до достижения общего понимания; собирает `docs/BRIEF.md` до единой строчки кода. С пользователем — по-русски, артефакты — по-английски. |
| `draft-product-spec` | Превращает согласованный BRIEF в `docs/SPEC.md`, готовый для разработки: сценарии, критерии приёмки, явные non-goals. |
| `draft-tech-plan` | Готовит `docs/PLAN.md` и `docs/TASKS.md`: архитектура, выбор стека, карта файлов, вехи, параллельные потоки работ, стратегия тестирования. |
| `implement-product` | Реализует задачи из согласованных PLAN/TASKS через субагентов, дизайн-скилы и поиск актуальной документации. |
| `test-product` | Проверяет продукт автотестами и Playwright-проверками в браузере. По умолчанию скептичен — «должно работать» не принимается как доказательство. |
| `review-product` | Независимое ревью поставки: корректность, безопасность, UX, полнота — против `docs/SPEC.md`. |
| `deploy-product` | Выкладывает проверенную сборку в реальное окружение и доказывает, что она действительно работает — а не просто что команда деплоя завершилась с кодом 0. |
| `pause` | Аккуратно закрывает рабочую сессию: останавливает новую работу, стабилизирует дерево, гоняет тесты, коммитит и переписывает `docs/STATUS.md`, чтобы следующая сессия могла продолжить без домыслов. |

## Вспомогательные скилы (6)

| Скил | Что делает |
|---|---|
| `coding-discipline` | Поведенческие ограничители против типичных ошибок LLM при написании кода: сначала подумать, простота прежде всего, точечные правки, циклы с проверкой цели. |
| `concise-mode` | Экономный по токенам режим общения: убирает воду и нарратив, сохраняя все факты, пути, команды и тексты ошибок. |
| `secure-review` | Обзор безопасности прикладного кода: секреты, авторизация, инъекции, XSS/CSRF, опасные настройки по умолчанию, гигиена зависимостей. |
| `web-design-guidelines` | Проверка UI-кода на соответствие Web Interface Guidelines — доступность и общепринятые лучшие практики. |
| `frontend-design` | Помощь в самобытном визуальном оформлении интерфейса: направление стиля, типографика, решения, не выглядящие шаблонными дефолтами ИИ. |
| `ui-quality-audit` | Необязательный read-only аудит UI/UX и фронтенд-архитектуры по эвристикам Nielsen, WCAG 2.2 AA и WAI-ARIA APG, с планом улучшений на фактах. Кода не меняет. |

## Агенты (5)

| Агент | Роль |
|---|---|
| `product-planner` | Продуктовый discovery и спецификации: ведёт интервью по требованиям, готовит `BRIEF.md`/`SPEC.md`. |
| `architect` | Прагматичный архитектор: выбор стека, системный дизайн, `PLAN.md` и `TASKS.md`. |
| `implementer` | Реализует назначенные задачи из `TASKS.md` в рамках выделенных путей. |
| `tester` | Придирчивый QA: автотесты и проверка в браузере через Playwright. |
| `reviewer` | Независимый ревьюер поставки: полнота, безопасность, UX, критерии готовности — по возможности read-only. |

## Структура репозитория

```
.claude-plugin/plugin.json   — манифест плагина (name: product-factory)
skills/                      — все 16 скилов (10 пайплайна + 6 вспомогательных), каждый в своей папке
agents/                      — 5 файлов агентов
templates/                   — шаблоны BRIEF/SPEC/PLAN/TASKS/STATUS/DECISIONS/REVIEW/HANDOFF/RELEASE
CLAUDE.product-factory.md    — блок для вставки в CLAUDE.md проекта
SKILLS-GUIDE.md              — шпаргалка на русском: какой скил в какой момент, советы по управлению
                                сессией, подводные камни с именами. Написана для человека, не для Claude.
```

## Заметки по устройству

- **Разрешение имени плагина.** Все внутренние ссылки между скилами (например, `orchestrate-product`,
  который отсылает к `discover-requirements`) используют короткое имя. `orchestrate-product/SKILL.md`
  и `iterate-product/SKILL.md` дополнительно умеют повторить попытку с префиксом `product-factory:`,
  если короткое имя не сработало при запуске через плагин — так что худший случай стоит один лишний
  вызов инструмента, а не тихий пропуск.
- **`pause` не хранит внутри себя команду тестов конкретного проекта.** Он всегда сначала ищет
  задокументированную команду в `CLAUDE.md`/`package.json`/`Makefile` целевого проекта и только потом
  действует — так скил остаётся рабочим в любом стеке, а не только в том, где он был написан.
- Скилы `code-review` и `simplify`, упоминаемые в некоторых из них, отдельно устанавливать не нужно —
  они встроены в сам Claude Code.
