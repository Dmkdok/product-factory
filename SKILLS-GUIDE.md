# Гайд по скиллам product-factory

Ты не обязан запоминать всё это наизусть. Скиллы почти всегда подключаются сами — по описанию
задачи или по команде `/имя-скилла`. Этот файл — шпаргалка на случай «а что сейчас происходит и
почему Claude делает именно это» в любом проекте, где установлен этот пакет.

Цель — не просто рабочий код, а продукт, который в будущем можно кому-то передать или показать
глобально и не краснеть. Поэтому фазы теста, ревью и безопасности ниже — не бюрократия, их нельзя
молча пропускать, даже если «и так работает».

## Главное правило: без слова «утверждаю» код не пишется

Пока ты не увидел план (`SPEC.md` / `PLAN.md` / `TASKS.md`) и не сказал явно **«утверждаю»** —
Claude не имеет права писать код продукта. Это защита от ситуации «наговорили лишнего, а потом
переделывать половину». Если Claude начал писать код без твоего утверждения — это баг процесса,
останови и напомни правило.

## Шпаргалка: какой момент — какой скилл

| Момент | Что вызвать | Что получишь |
|---|---|---|
| Начинаю совсем новый проект / сайт / приложение с нуля | `/orchestrate-product` (или просто опиши задачу словами — подключится сам) | Полный путь: интервью → спецификация → план → **твоё утверждение** → код → тесты → ревью |
| У продукта уже есть `docs/SPEC.md`, и нужно что-то добавить/поправить/ускорить | `/iterate-product` | Тот же путь, но короче: сверка с тем, что уже есть, оценка риска для старого функционала, и снова гейт утверждения перед кодом |
| Открыл проект после перерыва, не помню, на чём остановились | Ничего не вызывай — просто напиши «продолжаем» | Claude сам читает `docs/STATUS.md` — это и есть точка возврата |
| Заканчиваю работу на сегодня / закрываю сессию | `/pause` | Claude доводит дерево до стабильного состояния, прогоняет тесты, коммитит, обновляет `docs/STATUS.md` — следующий диалог продолжит без пересказа |
| Прошу код короче / проще / без лишнего | ничего — `coding-discipline` следит за этим всегда во время кодирования | Минимум кода, никакой самодеятельности сверх задачи |
| Говорю «кратко» / «экономь токены» | подключается сама `concise-mode` | Тот же смысл, без вступлений и пересказа своих действий |
| Нужна отдельная, более глубокая проверка UI/UX сверх обычного ревью | `/ui-quality-audit` (только по прямой просьбе, не сама по себе) | План улучшений по эвристикам Nielsen, WCAG, HIG — без правок кода |
| Нужно быстро проверить один диф на баги, без всего пайплайна | `/code-review` (встроенный, не из этого пакета) | Быстрый разбор текущих изменений |
| Хочу реально посмотреть на запущенное приложение, не только на тесты | `/run` (встроенный) | Приложение запускается, можно посмотреть глазами / сделать скриншот |

## Как выглядит путь нового продукта

```
discover-requirements → draft-product-spec → draft-tech-plan → [ТЫ: "утверждаю"] →
implement-product → test-product → review-product → готово к сдаче
```

Каждая стрелка — это отдельный скилл, но вызывать их по одному вручную не нужно:
`orchestrate-product` проводит по всем шагам сам, спрашивает то, что важно, и останавливается
перед кодом, ожидая твоё «утверждаю».

Для уже существующего продукта то же самое делает `iterate-product`, только начинает не с нуля, а
со сверки того, что меняется, с тем, что уже работает — чтобы не сломать старое, чиня новое.

## Правило: когда начинать новый диалог, а когда продолжать этот

Каждое сообщение в диалоге остаётся в памяти модели до конца разговора. Чем длиннее и «пёстрее»
диалог, тем хуже модель следует инструкциям и тем дороже каждый следующий ответ — это не мнение,
а прямая рекомендация Anthropic: «производительность падает по мере заполнения контекста».

**Начни новый диалог, если:**

- Берёшься за задачу, не связанную с текущей. Смешение тем в одном диалоге — самая частая причина
  «Claude что-то путает».
- Поправил Claude на одну и ту же ошибку два раза, и не помогло. Дальше в контексте — только
  неудачные попытки; новый диалог с более точным промптом почти всегда решает быстрее.
- Только что вызвал `/pause`. Он для этого и существует: закрыть диалог так, чтобы следующий начал
  чисто, подхватив прогресс из `docs/STATUS.md`, а не из прокрутки истории чата.
- Нужен непредвзятый взгляд на только что написанный код (ревью). Диалог, который сам писал код,
  склонен считать его нормальным; свежий диалог видит диф без этой предвзятости.
- Переходишь к следующей крупной фазе после того, как план утверждён. План уже лежит в
  `PLAN.md`/`TASKS.md` — он не потеряется, а вот полдиалога обсуждений плана в контексте во время
  кодирования — лишний шум.

**Продолжай тот же диалог, если:**

- Всё ещё разбираешься с одной и той же задачей, идёшь туда-сюда (отладка, уточнения) — история
  переписки тут не мусор, а полезная память, которую дорого пересказывать заново.
- Просишь мелкую правку по только что написанному коду.

Не бойся закрыть диалог: весь важный прогресс всегда лежит в `docs/` (`STATUS.md`, `TASKS.md`,
`PLAN.md`, `DECISIONS.md`), а не в голове у чата. Новый диалог подхватывает это за секунды.

## Похожие названия — не перепутай

Три скилла касаются интерфейса, но делают разное:

| Скилл | Когда срабатывает | Что делает |
|---|---|---|
| `frontend-design` | Пока интерфейс *строится* (фаза кода) | Творческие указания: как не сделать дизайн шаблонным — шрифты, цвета, композиция |
| `web-design-guidelines` | На ревью, по умолчанию, без запроса | Механически сверяет код с чек-листом Web Interface Guidelines |
| `ui-quality-audit` | Только если прямо попросить отдельный UX-аудит | Отдельный, необязательный, более глубокий разбор поверх обычного ревью |

## Об имени `discover-requirements`

Этот пакет собран из проекта `portfolio`, и один скилл там называется иначе: `elicit-requirements`.
Здесь переименован в `discover-requirements` — единственная причина в том, что «elicit» мало кто из
новичков знает. Остальные 9 pipeline-скиллов и 6 зависимых оставлены как есть, уже читаются понятно
без перевода. Если сверяешь этот пакет построчно с `portfolio`'s `.claude/skills/` — это
единственное расхождение, не баг синка: там имя менять нельзя (завязано на историю проекта и на
собственный `CLAUDE.md`), здесь — можно, свежая история ещё не накопилась.

## Встроенные скиллы Claude Code (не из этого пакета)

Эти идут вместе с Claude Code и полезны в моменте, вне большого пайплайна:

- `/code-review` — быстрый разбор текущего диффа на баги без полного цикла ревью.
- `/run` — запускает приложение по-настоящему, чтобы посмотреть на результат, а не только на тесты.
- `/security-review` — отдельная проверка безопасности вне `secure-review` (тот уже встроен в
  Phase 6 обычного пайплайна).

## Как начать новый проект этим пакетом

Создал новую папку под будущий проект — что дальше.

**Универсальные 6 скиллов** (`coding-discipline`, `concise-mode`, `secure-review`,
`web-design-guidelines`, `frontend-design`, `ui-quality-audit`) уже лежат в `skills/` этого пакета —
отдельно ставить не нужно. На машине, где собран этот пакет, они к тому же синхронизированы в
`~/.claude/skills/` и работают глобально в любой папке без копирования; на другой машине этого нет,
но копирование ниже отдаёт тот же результат.

**Нужен ли `CLAUDE.md` в новом проекте?** Не обязателен — гейт «утверждаю» и языковая политика (чат
по-русски, доки по-английски) зашиты прямо в `orchestrate-product` и в агента `product-planner`,
сработают и без него. Но лучше создать: без `CLAUDE.md` Claude не увидит явное «для нового проекта —
`orchestrate-product`» и будет полагаться только на то, что угадает по формулировке задачи, а
`pause` не будет знать, где искать тестовую команду именно этого проекта.

### Шаги

1. Создай папку проекта.
2. Скопируй в неё скиллы, агентов и шаблоны из этого пакета:

```powershell
$new = "C:\путь\до\новой\папки"   # поменяй на свою
$pack = "C:\Users\dmkdok\Desktop\product-factory"   # путь до этого пакета

New-Item -ItemType Directory -Force "$new\.claude\skills", "$new\.claude\agents", "$new\templates\product-factory" | Out-Null

Copy-Item "$pack\skills\*"                    "$new\.claude\skills"    -Recurse
Copy-Item "$pack\agents\*"                    "$new\.claude\agents"    -Recurse
Copy-Item "$pack\templates\*"                 "$new\templates\product-factory" -Recurse
Copy-Item "$pack\CLAUDE.product-factory.md"   "$new\CLAUDE.md"
```

3. Открой `$new` в VS Code, запусти Claude Code.
4. Опиши, что строишь (или явно `/orchestrate-product`) — весь пайплайн уже скопирован локально,
   работает без обращения к `$pack`.

### Альтернатива без копирования файлов

Для разовой пробы без файлов в новом проекте — `claude --plugin-dir "<путь до этого пакета>"`.
Нюансы (namespaced-вызовы `/product-factory:...`, что не проверено на практике) — в
[README.md](README.md) этого пакета, разделы «Try it in another project» и «Plugin name
resolution».

## Экономия токенов — как добавить в новый проект

`CLAUDE.product-factory.md` этого пакета пока **не включает** блок «Context economy» — это
доработка, которая осталась только в собственном `CLAUDE.md` проекта `portfolio`, не часть шаблона.
Если хочешь тот же эффект в новом проекте — добавь в его `CLAUDE.md` руками:

```
## Context economy

- Фан-аут-поиск ("где лежит X?") — через агента `Explore`, с `model: "haiku"` явным параметром на
  вызове `Agent`. Это инструкция делегирования, не значение по умолчанию у самого инструмента.
- При авто-сжатии контекста сохраняй: точку возврата из `docs/STATUS.md`, открытый milestone из
  `TASKS.md`, последние числа тестов/линта. Остальное можно ронять.
- Долгий разнородный диалог, ушедший в несвязанную задачу, или одна и та же правка, не помогающая
  Claude второй раз подряд — скажи прямо и предложи `/clear`, а не продолжай в засорённом контексте.
```

Это не автоматика этого пакета — просто рекомендованный текст, доказавший пользу в `portfolio`.
